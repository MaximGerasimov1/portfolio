orchestration

Переезд микросервисного приложения в Kubernetes

То же приложение описывается собственными манифестами Kubernetes вместо стека Docker Swarm.

Задача

Приложение было описано под Docker Swarm — одним compose-файлом. Нужно было перевести его на Kubernetes: описать конфигурацию, секреты, поды и сервисы своими манифестами, а затем выяснить, как две стратегии обновления влияют на простой приложения.

Что сделано

  • Разделил конфигурацию и секреты. Хосты и порты сервисов, адреса Postgres и RabbitMQ, имена шести баз — в ConfigMap environments. Пароль и логин БД, учётные данные RabbitMQ и ключи межсервисной авторизации — в Secret svc-secrets. Контейнеры получают их через envFrom, а не из захардкоженных значений в деплойментах.
  • Инициализация БД через ConfigMap. SQL-скрипт создания шести баз положил во второй ConfigMap и примонтировал как том в /docker-entrypoint-initdb.d/ контейнера Postgres — база поднимается с нужной схемой без ручных шагов.
  • Описал деплойменты и сервисы для всех девяти компонентов (postgres, rabbitmq и 7 сервисов приложения) в отдельном неймспейсе, по одной реплике на компонент.
  • Замерил время переразвёртывания. Написал deploy.sh, который применяет манифесты и ждёт kubectl rollout status по каждому деплойменту, засекая общее время. Прогнал обновление образов дважды — со стратегией Recreate и со RollingUpdate (maxUnavailable: 1, maxSurge: 1) — и сравнил результаты.

Фрагмент

# deploy.sh — замер времени выката

start_time=$SECONDS
kubectl apply -f ./manifests/
for deploy in $(kubectl get deployments \
      -n basic-kuber -o name); do
  kubectl rollout status "$deploy" -n basic-kuber
done
echo "Обновление: $(( SECONDS - start_time )) с."

# deployments.yaml — стратегия обновления

strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 1
    maxSurge: 1

Результат

  • Приложение разворачивается применением манифестов, без ручной настройки контейнеров; конфигурация и секреты меняются отдельно от описания деплойментов.
  • Схема базы создаётся автоматически при первом старте Postgres.
  • Замер показал, какая из двух стратегий даёт меньший простой при обновлении образов — это стало основанием оставить RollingUpdate стратегией по умолчанию.
