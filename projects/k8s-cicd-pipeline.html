CI/CD-пайплайн для приложения в Kubernetes

Приложение из Helm-чарта выкатывается в кластер k3s автоматически, из пайплайна GitLab CI.

Задача

Чарт уже был, но выкат делался руками: зайти на мастер-узел, выполнить helm upgrade, отдельно прогнать тесты. Ошибка сборки или несобирающийся сервис обнаруживались уже после выката. Нужно было собрать конвейер, который сам собирает семь сервисов, гоняет модульные и функциональные тесты и разворачивает приложение, — а ручным остаётся только решение «выкатить релиз».

Что сделано

  • Развернул GitLab Runner внутри кластера. Отдельный неймспейс, установка официальным Helm-чартом, регистрационный токен — в Kubernetes Secret, остальная конфигурация (executor kubernetes, образ job'ов, лимиты CPU и памяти) — в файле values. Job'ы пайплайна запускаются как поды в кластере.
  • Настроил RBAC раннера. Изначально прав хватало только на управление job-подами в своём неймспейсе, и стадия выката падала: helm upgrade обращается к API из самого job'а и создаёт объекты в неймспейсе приложения. Расширил правила (deployments, configmaps, ingresses, certificates, PV/PVC, секреты с list и patch — Helm ведёт учёт релизов в секретах) и включил clusterWideAccess, чтобы чарт сгенерировал ClusterRole вместо привязанной к неймспейсу Role. Отдельно указал service_account в конфигурации executor'а — по умолчанию job-под получал default и прав не наследовал.
  • Собрал пайплайн из трёх стадий: build — сборка семи Spring Boot сервисов через Maven Wrapper; test — модульные тесты Maven и функциональные тесты через newman, оба с выгрузкой JUnit-отчётов в артефакты; staging — helm upgrade --install. Первые две запускаются автоматически на ветках с префиксом feature_, третья — только по тегу и вручную.

Диагностика: что ломалось и почему

  • cd между строками script не сбрасывался — GitLab выполняет весь блок одним shell-процессом. Обернул каждую сборку в subshell (cd … && …).
  • Модульные тесты падали на contextLoads: тест поднимает полный Spring-контекст с JPA и RabbitMQ, а в CI-контейнере их не было. Добавил временные services: (postgres, rabbitmq) и полный набор переменных окружения job'а.
  • newman не резолвил доменное имя приложения внутри job-пода: имя было прописано только в /etc/hosts хоста, кластер о нём не знал. Добавил host_aliases (IP ingress-контроллера → имя) в конфигурацию раннера.
  • newman не проходил проверку самоподписанного TLS-сертификата — добавил флаг --insecure.
  • Конфликт Git LFS при пуше: .gitattributes требовал LFS для .jar, а maven-wrapper.jar оказался битым. Пересобрал wrapper через mvn -N wrapper:wrapper — новая версия использует скриптовую реализацию без .jar, и конфликт исчез.

Фрагмент

# .gitlab-ci.yml — правила запуска стадий

build_job:
  stage: build
  rules:
    - if: '$CI_COMMIT_BRANCH =~ /^feature_/'

staging_deploy:
  stage: staging
  image: alpine/helm
  script:
    - helm upgrade --install myapp src/helm/myapp
      -n basic-kuber --create-namespace
  rules:
    - if: '$CI_COMMIT_TAG'
      when: manual

# values раннера — SA и разрешение имени в поде

[[ runners ]]
  [ runners.kubernetes ]
    service_account = "gitlab-runner"
    image = "docker:stable"
    cpu_limit = "1000m"
    memory_limit = "1024Mi"
    [[runners.kubernetes.host_aliases]]
      ip = "192.168.33.11"
      hostnames = ["myapp.local"]

Результат

  • Ошибки сборки и интеграции выявляются на ветке feature_*, до выката: пайплайн не доходит до стадии staging.
  • Поставка воспроизводима — приложение разворачивается той же командой из того же чарта, независимо от того, кто выкатывает.
  • Ручных операций осталось две: поставить тег релиза и подтвердить выкат.
  • Ключи межсервисной авторизации убраны из репозитория: секрет создаётся отдельной командой, шаблон удалён из чарта, *.pem — в .gitignore.
