observability

Мониторинг, централизованные логи и алертинг

К приложению в Docker Swarm добавляются метрики, логи, дашборд и уведомления — чтобы причина сбоя находилась без обхода узлов по SSH.

Задача

Приложение работало в кластере из трёх узлов, но состояние сервисов приходилось выяснять вручную — заходить на узлы и читать docker service logs. Нужно было собрать метрики приложения и инфраструктуры в одном месте, централизовать логи всех контейнеров и узнавать об исчерпании ресурсов до того, как сервис перестанет отвечать.

Архитектура

Что сделано

  • Метрики приложения. Подключил Spring Boot Actuator и micrometer-registry-prometheus к четырём сервисам и описал прикладные счётчики через MeterRegistry: отправленные и обработанные сообщения RabbitMQ, число бронирований, запросы на gateway, запросы на авторизацию.
  • Сбор метрик. Prometheus снимает четыре job'а приложения через /actuator/prometheus, плюс инфраструктурные экспортёры: node_exporter (узлы), cAdvisor (контейнеры), blackbox_exporter (доступность эндпоинтов).
  • Обнаружение целей через DNS. Экспортёры развёрнуты в режиме global — по экземпляру на узел, поэтому их цели находятся через внутренний DNS Swarm (dns_sd_configs), а не задаются статическим списком: при добавлении узла конфигурацию Prometheus править не нужно.
  • Централизованные логи. Promtail в режиме global читает /var/lib/docker/containers на каждом узле и отправляет логи в Loki; Loki и Prometheus подключены в Grafana как источники данных через provisioning.
  • Дашборд. Собрал в Grafana панель на PromQL (метрики сервисов, CPU и память узлов и контейнеров) и LogQL (логи в разрезе сервисов).
  • Алертинг. Три правила: доступная память узла меньше 100 МБ, память контейнера больше 1 ГБ, загрузка CPU сервисом выше 10%. Alertmanager отправляет уведомления в Telegram и на почту по собственному шаблону сообщения.
  • Развёртывание стенда. Vagrantfile поднимает три ВМ, скрипты ставят Docker, инициализируют Swarm и разворачивают три стека. Скрипт деплоя ждёт готовности всех трёх узлов, прежде чем выполнять stack deploy.

Фрагменты конфигурации

# prometheus.yml — обнаружение целей через DNS Swarm

- job_name: 'node_exporter'
  dns_sd_configs:
    - names:
        - 'tasks.monitoring_node-exporter'
      type: 'A'
      port: 9100

# alert.rules.yml — правило по памяти узла

- alert: Доступная память на узле
  expr: node_memory_MemAvailable_bytes
        / 1024 / 1024 < 100
  for: 30s
  annotations:
    summary: "Доступно {{ $value }} Мб RAM"

Результат

  • Метрики приложения, контейнеров и узлов и логи всех сервисов собраны в одном интерфейсе — причина сбоя локализуется без обхода узлов по SSH.
  • Исчерпание памяти или рост CPU видно по алерту до того, как сервис перестанет отвечать.
  • Список целей мониторинга не нужно править руками при изменении состава кластера.
